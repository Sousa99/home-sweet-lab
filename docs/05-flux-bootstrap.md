# 05 — Flux bootstrap

Status: documented; not yet executed. Run this phase after Phase 2 is reviewed.

## Where Flux runs

| Component | Location | Role |
| --------- | -------- | ---- |
| `flux` CLI | Development machine (Mac) | Bootstrap, reconcile, inspect, debug |
| Flux controllers | DietPi k3s, namespace `flux-system` | Watch Git and reconcile the cluster |
| Git repository | GitHub `Sousa99/home-sweet-lab` | Source of truth |

The DietPi does not need the Flux CLI. The CLI uses the kubeconfig from
[04-kubeconfig-and-lens.md](04-kubeconfig-and-lens.md) to install the controllers, then pushes the
bootstrap manifests to GitHub. After that, the controllers poll GitHub outbound. No inbound access
to the cluster is required.

## Prerequisites

- Working `kubectl` access to the cluster.
- The `home-sweet-lab` repository exists (it does) and is public.
- A GitHub credential with repository write access.
- Outbound HTTPS from DietPi to GitHub and GHCR.

The development machine already has `gh` authenticated as `Sousa99` with `repo`, `workflow`, and
`read:org` scopes. That is sufficient for bootstrap, including deploy-key creation.

### Token options

Prefer a short-lived use of the existing `gh` token:

```bash
export GITHUB_TOKEN="$(gh auth token)"
```

Or use a dedicated classic PAT with the `repo` scope. For a fine-grained token, grant:

- **Contents**: Read and write
- **Administration**: Read and write (deploy keys)
- **Metadata**: Read

Do not write the token to a file, shell history, or this repository. Unset it when done:

```bash
unset GITHUB_TOKEN
```

## Install the Flux CLI

```bash
brew install fluxcd/tap/flux
flux --version
flux check --pre
```

`flux check --pre` validates that the cluster meets the prerequisites. It must pass before
bootstrap.

## Bootstrap

Run from the development machine, not on DietPi:

```bash
export GITHUB_TOKEN="$(gh auth token)"

flux bootstrap github \
  --owner=Sousa99 \
  --repository=home-sweet-lab \
  --branch=main \
  --path=clusters/dietpi \
  --personal \
  --read-write-key

unset GITHUB_TOKEN
```

`--read-write-key` is required for image automation: Flux must be able to push the updated image tag
back to `main`. Without it, the deploy key is read-only and image updates cannot be committed.

What the command does:

1. Creates or reuses the repository.
2. Creates a deploy key and stores it in the cluster as the `flux-system` secret.
3. Commits `clusters/dietpi/flux-system/` to `main`.
4. Installs the Flux controllers in the `flux-system` namespace.
5. Creates the `GitRepository` and root `Kustomization` that reconcile `clusters/dietpi`.

The repository content is not replaced. Existing README, docs, constitution, and spec files remain.

## Verify

```bash
flux check
flux get sources git -A
flux get kustomizations -A
kubectl -n flux-system get pods
kubectl get crd | grep -i flux
```

Expected:

- All Flux controllers are `Running`.
- `flux-system` Git source is `Ready` and has a recent revision.
- `flux-system` Kustomization is `Ready`.
- The repository now contains `clusters/dietpi/flux-system/`.

Commit and push confirmation:

```bash
git pull --ff-only
git log --oneline -5
```

```text
clusters/dietpi/
├── flux-system/              # generated by bootstrap; do not hand-edit unless recovering
│   ├── gotk-components.yaml
│   ├── gotk-sync.yaml
│   └── kustomization.yaml
├── infrastructure.yaml       # Kustomization for infrastructure/

```

`infrastructure.yaml` and `apps.yaml` are added in later phases. The root Kustomization recursively
reconciles the files in `clusters/dietpi/`.

## Day-2 operations

```bash
# Force a Git fetch and reconcile.
flux reconcile source git flux-system
flux reconcile kustomization flux-system --with-source

# Inspect.
flux get all -A
flux logs --all-namespaces --follow
flux events --for Kustomization/flux-system

# Trace where an object came from.
flux trace deployment/home-assistant -n home-assistant

# Pause automation during maintenance, then resume.
flux suspend kustomization apps --namespace=flux-system
flux resume kustomization apps --namespace=flux-system
```

Changes are made by committing to Git and letting Flux reconcile. `kubectl apply` is reserved for
bootstrap, manual Secrets, state uploads, and break-glass recovery.

## Recovery

If the Flux installation is lost but the repository is intact, re-run the bootstrap command. Flux
reuses the existing deploy key and reconciles the repository.

If the repository is lost, restore it from the development machine's clone or from GitHub's
recycle bin before re-bootstrapping. The cluster does not hold the only copy of the manifests.

If a Kustomization is stuck, inspect it before deleting anything:

```bash
flux get kustomization -A
kubectl -n flux-system describe kustomization <name>
kubectl -n flux-system logs deploy/kustomize-controller
```

## Uninstall

```bash
flux uninstall --namespace=flux-system
```

This removes Flux and its namespace. It does not delete workloads created by Flux unless they are
also removed. Export state and backups first.

## Troubleshooting

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| `401 Unauthorized` during bootstrap | Token expired or lacks repo access | Re-export a valid token |
| `403` creating deploy key | Token lacks repository administration | Use a classic `repo` token or grant Administration write |
| `Kustomization not ready` | Referenced manifests or CRDs missing | Inspect `flux get kustomizations -A` and controller logs |
| Image automation cannot push | Bootstrap used a read-only deploy key | Re-bootstrap with `--read-write-key` or configure a write credential |
| Repository shows no `flux-system` commit | Wrong owner/repository/path | Check the bootstrap output and `git log` on `main` |
