## Install

Install k3s after Tailscale is enrolled and the host has a tailnet address. The Tailscale IP is
added to the API certificate so the development machine can connect without an SSH tunnel.

```bash
sudo mkdir -p /etc/rancher/k3s
sudo tee /etc/rancher/k3s/config.yaml >/dev/null <<'EOF'
tls-san:
  - <dietpi-tailscale-ip>
EOF

curl -sfL https://get.k3s.io | sudo sh -
```

If k3s is already installed before the tailnet address exists, add the address to
`/etc/rancher/k3s/config.yaml` and restart k3s so the serving certificate is regenerated:

```bash
sudo systemctl restart k3s
```

The default Traefik and `local-path` components are kept. Do not disable Traefik; Home Assistant
uses it as the ingress.

## Verify

```bash
sudo systemctl status k3s --no-pager
sudo systemctl is-enabled k3s
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -A
sudo k3s kubectl get storageclass
sudo k3s kubectl get ingressclass
sudo k3s kubectl -n kube-system get service traefik -o wide
```

Expected: node `dietpi` is `Ready`, `local-path` is the default storage class, `traefik` is the
default ingress class, and the Traefik service has a load-balancer address.

Check the API certificate SANs before copying the kubeconfig:

```bash
sudo openssl x509 \
  -in /var/lib/rancher/k3s/server/tls/serving-kube-apiserver.crt \
  -noout -text | grep -A2 'Subject Alternative Name'
```

## Storage

k3s ships the Rancher `local-path` provisioner. It creates a directory per PersistentVolumeClaim
under `/var/lib/rancher/k3s/storage/`.

| Property | Value |
| -------- | ----- |
| Provisioner | `rancher.io/local-path` |
| Binding mode | `WaitForFirstConsumer` |
| Reclaim policy | `Delete` |
| Volume expansion | Not supported |
| Replication | None |
| Snapshots | None |

A lost volume is a lost volume. Application-level backups and the state bundle are the recovery
path. The PVC does not provide a snapshot or `kubectl cp`-free upload mechanism; see
[07-secrets-and-unsynced-state.md](07-secrets-and-unsynced-state.md).

## Ingress

Traefik is exposed by k3s's service load balancer. The service advertises the node's primary LAN
address, but its host ports bind all interfaces, so the tailnet address works:

```bash
curl -I "http://<dietpi-tailscale-ip>/"
```

With no ingress route defined, a `404` from Traefik is expected. Once Home Assistant has an
`IngressRoute`, the same address serves the UI. Ports 80 and 443 are bound by the Traefik service
load balancer; do not also run Tailscale Serve on 443 without first changing this layout.

## Backup before upgrades

k3s uses SQLite (kine) by default. Back up the datastore while k3s is stopped:

```bash
sudo systemctl stop k3s
sudo cp -a /var/lib/rancher/k3s/server/db \
  "/root/k3s-db-backup-$(date +%Y%m%d-%H%M%S)"
sudo cp -a /etc/rancher/k3s \
  "/root/k3s-config-backup-$(date +%Y%m%d-%H%M%S)"
sudo systemctl start k3s
```

Also keep the node token and any kubeconfigs outside Git. Never copy `/var/lib/rancher/k3s/server/`
into a public repository.

## Upgrade

Check the target release and read the k3s release notes first. Then:

```bash
sudo systemctl stop k3s
curl -sfL https://get.k3s.io | \
  sudo INSTALL_K3S_VERSION='vX.Y.Z+k3s1' sh -
sudo systemctl status k3s --no-pager
sudo k3s kubectl get nodes
```

Flux workloads restart automatically. Verify Home Assistant and the ingress after the node returns.

## Uninstall

```bash
sudo /usr/local/bin/k3s-uninstall.sh
```

This removes the cluster and its local volumes. Export any state bundle and backups first.

## Troubleshooting

```bash
sudo journalctl -u k3s --no-pager -n 100
sudo systemctl status k3s --no-pager
sudo k3s kubectl get events -A --sort-by=.lastTimestamp | tail -30
```

- API unreachable from the development machine: confirm Tailscale is up and the Tailscale IP is in
  `tls-san` and the certificate SANs.
- Pods stuck `Pending`: inspect the PVC and storage class.
- Ingress returns `404`: confirm the `IngressRoute` exists and the host/path rule matches.
- Node `NotReady`: check disk space, memory pressure, and `journalctl`.
